# Operations dashboard

> داشبورد RTL و API محلی برای پایش ناوگان AMR و مدیریت مأموریت‌های نمونه.

## مسئولیت‌ها
- نمایش شمارش واقعی ربات‌های آنلاین، میانگین باتری و مأموریت‌های فعال.
- نمایش موقعیت نسبی ربات‌ها و جدول آخرین telemetry ذخیره‌شده.
- نمایش هشدارهای باتری کم، آفلاین بودن ربات و مأموریت‌های در صف.
- جست‌وجو و فیلتر مأموریت‌های اخیر، فرم native برای ایجاد/تخصیص/لغو.
- نمایش metadata حمل مأموریت شامل بار، اولویت، deadline و منبع manual/WMS.
- ارائهٔ نقشهٔ گرافی، مسیر کوتاه و مانع موقت از API.
- دریافت eventهای نسخه‌دار WMS با امضای HMAC و idempotency.
- دریافت پیام‌های VDA 5050 (state و connection) از gateway و محاسبهٔ آفلاین از تازگی heartbeat.
- نمایش توقف اضطراری و ورود به میدان حفاظتی به‌عنوان هشدار.
- ارائهٔ گزارش پایهٔ مأموریت، ناوگان و تعداد نمونه‌های telemetry.
- نمایش صف کار اولویت‌دار، تحلیل عملیات و گزارش ممیزی در داشبورد.
- نمایش صادقانه وضعیت prototype و نبود اتصال مستقیم سخت‌افزار.

## قراردادهای API
- `GET /api/alerts` — هشدارهای عملیاتی فعلی.
- `GET /api/reports` — KPIهای پایهٔ تجمعی.
- `GET /api/map` — گره‌ها، یال‌ها و موانع فعال.
- `POST /api/map/nodes|edges|obstacles|route` — مدیریت گراف و محاسبهٔ مسیر؛ مسیر با رزرو گره (`robot` و `reserve: true`) هم پشتیبانی می‌شود.
- `GET /api/map` — گره‌ها، یال‌ها، موانع، رزروهای فعال و تعارض‌ها.
- `GET|POST /api/chargers` — فهرست و ثبت شارژر؛ فهرست شامل `waiting` و `admit_now` صف شارژ است.
- `GET /api/robots/<id>/charge` — تصمیم dry-run شارژ و شارژر پیشنهادی.
- `POST /api/robots/<id>/charge` — ارسال ربات به شارژر آزاد (یا شارژر مشخص با `charger`).
- `POST /api/integrations/events` — event نسخهٔ ۱ با `X-Motiva-Signature`؛ برای event تکراری مأموریت جدید ساخته نمی‌شود.
- `POST /api/integrations/vda5050` — پیام `state` یا `connection` با `agv_id`؛ بدون secret (سطح جداگانه از webhook WMS) و فقط ورودی.
- `GET /api/missions/<id>/dispatch` — پیشنهاد تخصیص (dry-run) با امتیاز و علت کنارگذاشتن هر ربات.
- `POST /api/missions/<id>/assign` با `{"auto": true}` — تخصیص خودکار داخل همان تراکنش، همراه با توضیح انتخاب.
- `POST /api/map/nodes` مختصات اختیاری `x` و `y` (۰ تا ۱۰۰) را می‌پذیرد تا امتیاز فاصله ممکن شود.
- `GET /api/missions/queue` — مأموریت‌های در صف به ترتیب تخصیص (اولویت، سپس ددلاین، سپس ترتیب ایجاد).
- `POST /api/missions/<id>/complete` — تکمیل مأموریت در حال اجرا، آزادسازی رزرو مسیر و ثبت ممیزی.
- `POST /api/map/rules` — `max_speed` و `restricted` هر zone؛ محدودیت ممنوعه از مسیر‌یابی حذف می‌شود، سرعت فقط ذخیره و ممیزی می‌شود.
- `GET /api/analytics?days=1|7|30` — ترکیب وضعیت مأموریت، نرخ تکمیل، نمونه‌های روزانه، فعال‌ترین ربات‌ها و سهم تخمینی حرکت با بلوک `definitions`.
- `GET /api/audit?limit=N` — گزارش ممیزی اقدمات (حداکثر ۵۰۰، جدیدترین اول).

## قراردادها / Edge cases
- API محلی از SQLite استفاده می‌کند؛ داده‌های ناوگان نمونه و مأموریت‌ها production نیستند.
- KPIهای کل از کل جدول محاسبه می‌شوند؛ جدول مأموریت فقط ۱۰ رکورد اخیر را نشان می‌دهد.
- در قطع API، عملیات غیرفعال و تازگی آخرین داده به کاربر اعلام می‌شود.
- مسیر در گراف بدون جهت محاسبه می‌شود و گره‌های دارای مانع فعال کنار گذاشته می‌شوند.
- webhook بدون secret پیکربندی‌شده یا signature معتبر پذیرفته نمی‌شود.
- ربات وقتی آفلاین است که heartbeat قدیمی‌تر از `MOTIVA_HEARTBEAT_TIMEOUT_SECONDS` داشته باشد یا هیچ heartbeat نداشته باشد؛ `status` گزارش‌شده جدا از `status` مشتق‌شده برگردانده می‌شود.
- ربات stale آنلاین شمرده نمی‌شود، هشدار باتری کم برایش جای هشدار آفلاین را نمی‌گیرد و مأموریت نمی‌گیرد.
- `actor` در درخواست‌ها رشتهٔ ورودی با پیش‌فرض `operator` است؛ انتساب نقش واقعی به احراز هویت issue #1 وابسته است.
- `audit_log` فقط append-only است؛ هیچ endpoint ای ردیف را تغییر یا حذف نمی‌کند، اما زنجیرهٔ tamper-evident ندارد.
- مختصات VDA بر حسب متر روی نقشهٔ ربات است و با `MOTIVA_MAP_EXTENT_METRES` به شبکهٔ ۰ تا ۱۰۰ تبدیل و clamp می‌شود.
- ساخت order خروجی VDA پیاده‌سازی شده اما هیچ چیزی روی `order/{agv_id}` منتشر نمی‌شود؛ هیچ endpoint ادعای ارسال فرمان به ربات ندارد.
- تخصیص خودکار ربات‌های `offline`، `charging`، باتری نامشخص و باتری زیر ۲۰ را با علت کنار می‌گذارد و بقیه را با وزن باتری ۰٫۴۰، بار کاری ۰٫۳۵ و فاصله ۰٫۲۵ رتبه‌بندی می‌کند.
- امتیاز فاصله فقط وقتی استفاده می‌شود که مبدأ مأموریت به گره نقشه دارای مختصات تبدیل شود؛ `distance_used` صریحاً گزارش می‌شود تا UI فاصلهٔ محاسبه‌نشده را القا نکند.
- وزن‌ها در صورت نبود یک سیگنال بازنرمال می‌شوند و تساوی امتیاز با شناسهٔ ربات قطعی می‌شود.
- رزرو فقط روی گره‌های میانی مسیر اعمال می‌شود؛ مبدأ و مقصد ایستگاه‌های مشترک‌اند و رزرو آن‌ها عبور دو مأموریت از یک ایستگاه را ناممکن می‌کرد.
- هر رزرو `held_until` دارد و رزرو منقضی در اولین claim بعدی پاک می‌شود؛ پیشرفت پیوسته‌ای برای آزادسازی گره هنگام عبور وجود ندارد.
- یک‌نگهدارنده به‌ازای هر گره در دیتابیس (PRIMARY KEY) تضمین می‌شود؛ رباتی که گره خودش را دوباره رزرو کند lease را تمدید می‌کند و تعارض نمی‌سازد.
- نتیجهٔ مسیر `clear`، `detoured`، `blocked_by_traffic` یا `no_route` است تا «نبود مسیر در نقشه» از «اشغال مسیر توسط ربات دیگر» قابل تفکیک باشد.
- محدودیت شناخته‌شده: رزرو در سطح گره و محدود به زمان است، نه پنجرهٔ زمانی هر یال؛ برخورد میان‌راهرو پس از انقضای lease و حل deadlock پوشش داده نمی‌شود.
- شارژ در آستانهٔ ۲۵٪ فعال می‌شود (۵٪ بحرانی) و ربات آفلاین، در حال شارژ یا با باتری نامشخص هرگز فرمان شارژ نمی‌گیرد.
- نزدیک‌ترین شارژر آزاد انتخاب می‌شود؛ درخواست شارژر اشغال‌شده `charger_unavailable` برمی‌گرداند و به‌صورت خاموش به شارژر دیگری تغییر نمی‌کند.
- یک ربات به‌ازای هر شارژر با PRIMARY KEY تضمین می‌شود؛ رباتی که `moving` یا `waiting` گزارش دهد (HTTP یا VDA) شارژر را فوراً آزاد می‌کند.
- رباتی که به‌دلیل اشغال همهٔ شارژرها رد می‌شود در `charger_queue` می‌ماند؛ ترتیب: بحرانی‌ها، سپس منتظران بیش از ۶۰۰ ثانیه (starvation)، سپس کمترین باتری، سپس بیشترین انتظار، سپس شناسه.
- هر ورودی صف `waited_seconds` و `escalated` را گزارش می‌کند؛ ربات بحرانی یا منتظر طولانی هشدار `charger_queue_stuck` با علت و مدت انتظار ایجاد می‌کند.
- `admit_now` فقط پیشنهاد می‌دهد؛ ربات با شارژ واقعی از صف خارج می‌شود.
- آستانهٔ تخصیص مأموریت از آستانهٔ شارژ مشتق می‌شود (`MIN_DISPATCH_BATTERY = CHARGE_THRESHOLD + 1`)، پس رباتی که واجد شارژ است مأموریت جدید نمی‌گیرد.
- صف با درخواست سرو می‌شود، نه worker پس‌زمینه؛ در سیستم بی‌کار، پذیرش تا فراخوانی `/api/chargers` یا درخواست شارژ رخ نمی‌دهد.
- مدل هزینه و منحنی شارژ (که VDA 5050 تعریف نمی‌کند) پوشش داده نشده است.- `MOTIVA_HOST` و `MOTIVA_PORT` قابل تنظیم‌اند (پیش‌فرض `127.0.0.1:8787`)؛ در کانتینر روی `0.0.0.0:8787` اجرا می‌شود و مسیر پوشهٔ دیتابیس را می‌سازد.
- `docker compose up -d --build` سرویس `app` و صفحهٔ فرود nginx را بالا می‌آورد؛ TimescaleDB، EMQX و Keycloak فقط با پروفایل `platform` فعال می‌شوند و کد فعلی از آن‌ها استفاده نمی‌کند.

## منابع کد
- `app/index.html` — رابط RTL، هشدارها، dialogهای native، فیلترها و وضعیت اتصال.
- `app/server.py` — API health/overview/robots/telemetry/missions/map/alerts/reports/integrations.
- `app/navigation.py` — مسیر کوتاه و رزرو گره‌های متعارض.
- `app/integration.py` — قرارداد event و HMAC.
- `app/dispatch.py` — امتیازدهی قابل‌توضیح تخصیص خودکار ربات.
- `app/traffic.py` — رزرو زمانی گره‌های مسیر و مسیر‌یابی با آگاهی از ترافیک.
- `app/charging.py` — تصمیم شارژ و تخصیص شارژر آزاد.
- `app/test_server.py` و `app/test_integration.py` — تست‌های API و قرارداد integration.
- `app/test_dispatch.py`، `app/test_vda5050.py`، `app/test_traffic.py` و `app/test_charging.py` — تست‌های واحد امتیازدهی، VDA 5050، رزرو ترافیک و شارژ.
- `Dockerfile`، `docker-compose.yml` و `.github/workflows/quality.yml` — بسته‌بندی کانتینر و بیلد/اسموک‌تست تصویر در CI.
